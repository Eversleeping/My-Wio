# 任务编排

从侧栏的「任务」选择项目，填写需求和验收条件。项目页可直接打开该项目的任务列表或创建草稿。首页显示最近任务。

## 从计划到执行

1. 为每个成员选定角色、引擎、工作区及权限模式。开发和审查建议使用不同工作树。三个角色可以使用不同引擎。
2. 录入步骤并选择依赖。一个步骤的全部依赖完成后才具备派单条件。依赖图和步骤列表使用同一份快照。编辑图中的节点可跳到相应表单，依赖环和缺失依赖会在节点旁标出。
3. 保存计划，在「执行授权」核对成员、目录、权限、并发和累计次数，再启动运行。共享目录的成员会访问同一批文件。
4. 在详情查看阻塞、历史尝试与原生会话。暂停保留在途尝试并停止新派单。取消会请求远端停止并等待证据。

## 成果与审查

开发步骤可选择「捕获成果」完成规则。开发轮次结束后，在「成果」选择来源尝试，逐行填写相对文件路径。系统保存所选修改及删除的 Git 基线、路径和内容摘要。一次捕获支持最多 64 个普通文件，基线和成果字节各限 1 MiB。跳过 Git 元数据、常见密钥路径和忽略的新增文件。

审查步骤选择「审查决定」完成规则，关联开发依赖的成果和至少一项验收条件，并指定独立的托管工作树。先从项目的 Git 操作创建工作树，使目标工作树的 HEAD 与成果基线一致。也可以在同项目的另一台 Agent 上创建工作树后选作目标。源与目标 Agent 都需要声明 `task.artifacts.v1`。

在成果卡片选择「准备工作区」并复现到审查成员的工作树。Agent 核对 Git 基线、文件和摘要，启动审查前再核对一次。也可以选择「仅执行整合预检」检查指定干净工作区。复现的改动保留为未提交文件。已有审查工作树可以用于新版成果，前提是其中仍为上次成功准备的准确内容。检查失败时，查看操作结果并处理工作区现状，或新建工作树。

审查轮次结束后，在「审查」逐项记录检查状态、证据、结论及理由。每个必需检查都通过才可记录审查通过。拒绝后可在授权预算内返工，系统重跑开发步骤及受影响的后继。旧审查、旧成果与失效记录可查。无法判断可记录原因并重审。全部必需步骤完成后，去「待验收」核对最终快照并记录用户决定。Git 提交、推送和部署仍使用各自的入口与授权。

## 成员协作与计划变更

执行授权可启用任务成员工具，目标 Agent 需要声明 `task.collaboration.v1`。工具的来源绑定到当前 Agent、会话和原操作。每次写入使用同一 `request_id` 对账。

| 工具 | 用途 |
| --- | --- |
| `wio_get_task_context` | 查询当前计划、收到的消息或原任务请求 |
| `wio_send_task_message` | 给授权计划中的另一成员留言 |
| `wio_request_task_review` | 为自己的开发成果请求计划中的后继审查 |
| `wio_report_task_blocker` | 报告阻塞，供协调成员与用户查看 |
| `wio_propose_task_plan` | 协调成员提交替换计划草案 |

审查请求沿用任务调度和成果版本检查。团队留言可在后续轮次读取。工作区、权限或成员扩大时，只有用户能创建新授权。用户可在旧运行结束后从团队请求查看并采用草案。新计划有自己的运行，旧执行结果和审查保留在历史。新运行重新执行该计划的步骤。

## 恢复运行

任务页刷新或重连会补读持久化快照。出现「执行状态未知」时，在 Agent 上独立核实远端进程已经停止，再填写停止时间与依据。已确认停止后，可在预算内重试。工作区交接状态未知时保留原工作树。若需要换审查工作树，可结束当前运行、更新计划并重新授权。普通会话仍可从统一会话页打开。

本地自动化用真实 HTTP、WebSocket、gRPC、Agent、Git 工作区与确定性的假引擎验证任务流程。官方 CLI 版本兼容、真实上游模型和生产升级需要分别验证。

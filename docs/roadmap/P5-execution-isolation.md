# P5 执行隔离

返回[路线图总览](README.md)。状态以总览的“进度总表”为准，本文件只写步骤细节和执行记录。

Wio 面向可信的单管理员环境，这一点不变。本阶段要防的不是恶意用户，而是被内容误导的模型：仓库里的文件、网页、工单文本都可能带着指令，而协作功能已经能让一个会话自动创建别的会话。目前模型运行的命令拥有 Agent 账号的全部权限，一个工作区里的问题可以波及这台服务器上的所有凭据。

本阶段先盘点、再做默认生效的低风险收紧，最后提供一个可选的隔离模式。隔离技术能不能在目标环境里用，要先验证再投入，所以 P5-03 的结论可以改写甚至取消后面的步骤。

## 现状

### Agent 账号能碰到什么

外部 Agent 以专用账号 `wio-agent` 运行，systemd 单元（`deploy/agent.service`）的限制是：`ProtectSystem=strict`、`ProtectHome=read-only`、`ReadWritePaths=/var/lib/wio-agent`、`NoNewPrivileges=true`、`PrivateTmp=true`，附加组 `docker`。注册时如果勾选免密 sudo，`internal/sshbootstrap/bootstrap.go` 的 `agentServiceUnit` 会把其中四项放开，并写入 `NOPASSWD: ALL`。

这些限制作用于整个 Agent 服务。AI CLI 是 Agent 的子进程，模型运行的命令又是 CLI 的子进程，它们和 Agent 是同一个账号、同一组限制，彼此之间没有边界。工作区、Agent 状态、凭据文件和账号的 HOME 都在 `/var/lib/wio-agent` 下面（`internal/agent/config.go` 的默认值）。

| 资源 | 位置 | 模型运行的命令能否触及 |
| --- | --- | --- |
| Agent 注册令牌 | `/etc/wio-agent/config.json`，属主是 Agent 账号 | 可读。拿到它就能以这台服务器的身份连接控制面 |
| Codex API 密钥 | `/etc/wio-agent/codex.key` | 可读 |
| Git 凭据 | `~/.git-credentials` | 可读 |
| Claude、Gemini 的托管配置 | 状态目录下的 `claude/api.json`、`gemini/api.json` | 可读 |
| 其他项目的工作区 | `/var/lib/wio-agent/projects` 下的其他目录 | 可读写 |
| 其他会话的原生历史 | `~/.claude`、`~/.codex`、`~/.gemini` | 可读写 |
| Docker | `/var/run/docker.sock`，通过 `docker` 组 | 可连接。Docker 权限接近 root |
| 依赖安装助手 | `/run/wio-prerequisites/helper.sock` | 可连接。助手只接受一个固定动作，不接受调用方给出的命令 |
| 其他会话的回环 MCP 令牌 | Claude 和 Codex 的进程参数里 | 同账号的进程可以读到别的进程的参数 |

上表里令牌、密钥、Git 凭据、托管配置、两个 socket 和进程参数这几行，已在一台外部 Agent 上用只读探测确认（只判断是否可读、是否可连接，不读取内容）。“其他工作区”和“原生历史”两行是由“同一账号、同一目录”推出来的，连同启用 sudo 的服务器和内置控制机的情况，由 P5-01 实测补齐。

### 子进程拿到的环境变量

- 非测试 Go 代码里有 6 处 `os.Environ()`：`claudeadapter/adapter.go`、`geminiadapter/adapter.go`、`codexadapter/adapter.go`、`deployer/deployer.go`、`gitrepository/safety.go`，以及自更新时重新执行自身的 `agent/exec_linux.go`。没有任何地方调用 `os.Unsetenv` 或 `os.Clearenv`。
- 三个适配器的做法都是“继承全部环境，再覆盖或追加自己管理的变量”。没有设置 `Env` 的命令（例如版本探测）直接继承全部环境。
- Claude 的托管密钥是个好例子：`configureEnvironment` 在支持的平台上通过管道文件描述符把 `ANTHROPIC_API_KEY` 交给 CLI，代码注释写明了原因，环境变量会被模型启动的每个命令看到。探测确认模型运行的命令里确实看不到这个变量。
- Codex 的密钥以 `WIO_CODEX_API_KEY` 放在 app-server 的环境里，Gemini 的密钥以 `GEMINI_API_KEY` 放在 CLI 的环境里。模型运行的命令能否看到它们，由 P5-01 确认。
- **内置控制机。** 它的 Agent 运行在控制面进程内（`cmd/controlplane/main.go`）。按代码阅读，AI CLI 子进程会继承控制面的 `WIO_MASTER_KEY`、`WIO_DATABASE_URL`、`WIO_SETUP_TOKEN`。容器以 root 运行，挂载了 Docker socket 和宿主机的 `/srv`、`/opt`、`/home`。这一条还没有在真实容器里验证，由 P5-01 确认。

### CLI 自带的限制没有形成边界

- Codex 的沙箱模式固定为 `danger-full-access` 并允许网络（`internal/codexconfig/config.go`）。注释里写了原因：Codex 自带的沙箱会阻止写 `.git`。
- Claude 的 `--permission-mode` 和 Gemini 的 `--approval-mode` 是模型层面的约束，决定模型要不要先征得同意，不是操作系统层面的限制。
- 控制面镜像设置了 `IS_SANDBOX=1`，它只是让 Claude 允许以 root 使用跳过权限检查的模式，不提供任何隔离。`docs/CLAUDE.md` 已经如实说明了这一点。

### 进程模型

隔离要加在进程启动的地方，所以先看清有哪些启动点。

| 引擎 | 进程模型 | 启动位置 |
| --- | --- | --- |
| Codex | 每个会话一个 app-server 进程，空闲 5 分钟回收；另有一个共享进程用于查询模型、技能等。启动时不设置工作目录，工作区在之后作为线程的 `cwd` 传入 | `codexadapter/adapter.go`、`codexadapter/sessions.go` |
| Claude | 每轮一个进程；技能发现另起一个短进程 | `claudeadapter/adapter.go`、`claudeadapter/skills.go` |
| Gemini | 每轮一个进程，或一个 ACP 进程；技能管理另起短进程 | `geminiadapter/adapter.go`、`geminiadapter/acp.go`、`geminiadapter/skills.go` |

非测试代码里共有 8 处直接调用 `exec.Command*`，另有 9 处通过 `internal/childprocess` 启动（Git、部署、扫描等）。

会话进程还依赖 Agent 在回环地址上开的几个服务：协作用的 MCP 桥接（`internal/mcpbridge`，随机端口加随机令牌）、Gemini 的提问和追加通道、Claude 的流式转发代理。任何隔离方案都必须放行这些回环连接。

## 目标

1. 有一份写下来的威胁模型：防什么、不防什么、每种部署形态下模型运行的命令实际能触及什么。
2. 默认生效的收紧：子进程只拿到它需要的环境变量；控制面的密钥不会出现在任何子进程的环境里。
3. 一个可选的隔离模式：开启后，会话进程只能写自己的工作区，读不到 Agent 令牌、其他凭据和其他工作区。
4. 界面和文档如实呈现当前的隔离状态，不让人误以为权限模式等于隔离。

不在本阶段范围内：

- 多租户，或防范恶意管理员。
- 限制会话的网络出口。CLI 必须访问模型接口，按域名限制出口是另一类工程。
- 每个会话一个容器。
- 改变 Agent 自身做部署和 Git 操作的权限。部署功能需要 Docker，这不变；变的是会话进程能不能借用它。
- 在启用免密 sudo 的服务器上提供隔离。两者目标相反，文档里写明即可。

## 设计

以下是方向性的草图。P5-01 的盘点和 P5-03 的验证结果可以修正它。

### 威胁模型（初稿）

| 项目 | 内容 |
| --- | --- |
| 要保护的东西 | Agent 注册令牌；各引擎的 API 密钥；Git 凭据；控制面的主密钥和数据库连接串；其他工作区的代码；宿主机本身 |
| 设想的威胁 | 模型被工作区内容、网页或工具输出里的指令误导，执行了读取凭据、改动别的项目或向外发送数据的命令；模型自己的失误 |
| 放大因素 | 协作功能可以自动创建子会话、跨工作区、跨引擎；定时任务在无人值守时运行 |
| 不设防的对象 | 管理员本人；已经拿到服务器 shell 的人；CLI 厂商和模型接口提供方 |
| 明确接受的残余风险 | 模型可以把自己工作区里的内容发到网络上；同一引擎的会话共用 CLI 的配置目录，能读到彼此的原生历史 |

### 分三层推进

| 层 | 内容 | 是否默认生效 | 步骤 |
| --- | --- | --- | --- |
| 盘点 | 把“能触及什么”变成一张有结论的表 | 不改行为 | P5-01 |
| 收紧 | 环境变量、令牌传递方式 | 默认生效 | P5-02 |
| 隔离 | 文件系统沙箱 | 可选，默认关闭 | P5-03、P5-04、P5-05 |

收紧这一层挡不住同账号进程读文件：令牌文件属于 Agent 账号，子进程也是这个账号。能挡住文件访问的只有隔离这一层。这个界限要在文档里说清楚，不要让“收紧”听起来像“隔离”。

### 环境变量

在 `internal/childprocess` 提供唯一的环境构造函数，所有启动子进程的地方都通过它设置 `Env`。分两步收紧：

1. **先去掉控制面的变量。** 任何子进程都不继承 `WIO_` 开头的变量，适配器显式传入的除外（`WIO_CODEX_API_KEY` 等）。这一步几乎没有兼容风险。
2. **再改成白名单。** 只传递通用的运行环境（`PATH`、`HOME`、语言与时区、临时目录、代理与证书相关变量），加上各引擎自己命名空间下的变量，并且只传给对应引擎的进程。白名单的具体内容由 P5-01 的盘点决定。Agent 配置里留一个追加变量名的出口。

第二步有兼容风险：文档写明了未应用托管预设时可以使用“服务环境认证”，也就是管理员在服务环境里自己设置的变量。白名单必须保住这条路。

对内置控制机要说实话：子进程和控制面是同一个账号，裁剪环境只能防止无意的泄露（例如模型运行 `env` 后输出被送到模型接口），挡不住有意读取。同账号的进程可以读到控制面进程的初始环境，也能连数据库。真正的边界要靠隔离模式，或者不在控制机上运行不可信的工作区。

### 隔离模式

思路是在启动 CLI 之前先套一层包装：由 Agent 二进制自己的一个子命令设置好访问规则，再执行真正的 CLI。规则对 CLI 和它启动的所有命令生效，并且不能被解除。

规则草案：

| 路径 | 访问 |
| --- | --- |
| 会话的工作区根目录 | 读写 |
| worktree 会话所属主仓库的 Git 目录 | 读写。否则在 worktree 里无法提交 |
| 该引擎的 CLI 配置目录 | 读写。续聊和分叉依赖它 |
| CLI 的安装目录、系统目录 | 只读、可执行 |
| 临时目录 | 读写 |
| `/etc/wio-agent`、状态目录里的凭据与其他内容、`~/.git-credentials` | 不可见 |
| 其他工作区、扫描根目录 | 不可见 |
| Docker socket、依赖安装助手的 socket | 不可连接 |

设计上已经确定的几点：

- **默认关闭，逐台服务器开启。** 开关放在 Agent 配置里，Agent 把实际状态上报给控制面。P4-02 已完成时用能力名声明，否则在心跳里加字段。
- **配置了却用不了时拒绝运行。** 内核不支持或规则应用失败时，会话以明确的错误结束，不要悄悄退回到无隔离。
- **隔离模式下模型不能自己推送代码，也不能使用 Docker。** 推送走 Wio 的 Git 面板，由 Agent 完成。这是它只能作为可选项的主要原因。
- **与免密 sudo 互斥。** 界面上不允许同时开启。
- **协作不受影响。** 跨工作区协作是通过在目标工作区创建子会话完成的，不需要会话进程直接读别的工作区。P5-03 要验证这一点。

技术选型见决策 D4：优先验证 Landlock，因为它不需要安装额外软件、不需要特权；bubblewrap 作为备选。两者能否满足上面的规则，尤其是能否挡住 Docker socket，由 P5-03 回答。

## 步骤

### P5-01 威胁模型与可达性盘点

**做法**

1. 把“设计”里的威胁模型初稿定稿，和用户确认“不设防的对象”和“明确接受的残余风险”两行。
2. 写一个只读的探测脚本（建议放在 `scripts/probe-session-reach.sh`）。它在会话进程的位置上逐项检查本文件“可达性清单”里的资源，只输出资源名和“可读、可写、可连接”的是或否。脚本不得输出任何文件内容、变量取值或令牌。
3. 在三种部署形态下，从一个真实会话里运行它：外部 Agent 默认配置、外部 Agent 启用 sudo、内置控制机。三种引擎各跑一次，因为它们传递密钥的方式不同。这一步需要用户配合或授权；做不了的形态在“执行记录”里注明。
4. 盘点子进程环境：列出各引擎的 CLI 进程和模型运行的命令里出现的环境变量名（只要名字），标出哪些是运行必需的、哪些是凭据、哪些不该出现。
5. 确认或否定“内置控制机的子进程继承控制面密钥”这一条，并更新总览“发现的问题”里对应的记录。
6. 盘点依赖宽权限的现有用法：模型自己执行 `git push`、模型使用 Docker、会话读取工作区之外的路径、依赖 sudo 的工作流。这些决定了隔离模式会让谁受影响。
7. 把结果填进“可达性清单”，每一行给出结论：P5-02 处理、P5-04 处理，或接受并写入文档。

**验收**

- “可达性清单”三种形态的列都有实测结果或“未能测试”的说明，每一行都有结论。
- 环境变量清单完成，可以直接作为 P5-02 白名单的输入。

**说明**

这一步不改产品代码。写进仓库的只有资源的类别和结论，不要写具体机器的主机名、地址、内核版本或任何取值。

### P5-02 子进程环境与凭据收紧

分两个提交，对应“设计”里环境变量的两步。

**提交一：去掉控制面的变量**

1. 在 `internal/childprocess` 增加环境构造函数和它的测试。
2. 8 处直接调用 `exec.Command*` 的地方和 9 处通过 `childprocess` 启动的地方，全部显式设置 `Env`。`claudeadapter` 的 `configureEnvironment` 在没有传入变量时会直接返回、保留全部继承；当前的调用方总会传入至少一个变量，不会走到这里，但这条路径也要改成经过公共函数。
3. `agent/exec_linux.go` 的自更新重新执行是 Agent 自己，保留完整环境。
4. 处理适配器测试自己用的变量。`claudeadapter` 和 `geminiadapter` 的测试把测试程序自身当作假 CLI，靠继承来的 `WIO_CLAUDE_TEST_CHILD`、`WIO_GEMINI_TEST_CHILD` 等变量切换模式；去掉 `WIO_` 开头的变量之后这些测试会失效。把这些测试变量改成不带 `WIO_` 前缀的名字，或者改为通过适配器显式传入的环境传递。不要为了测试在公共函数里开例外。
5. 新增一个扫描源码的测试：`os.Environ()` 只允许出现在公共函数和 `exec_linux.go` 里；直接调用 `exec.Command*` 的文件固定为一份清单，新增文件会让测试失败，提醒作者设置环境。
6. 同一提交里升级 `buildinfo.Version`。

**提交二：白名单**

1. 按 P5-01 的环境变量清单实现白名单和按引擎划分的命名空间。
2. Agent 配置增加“额外传递的变量名”字段，默认为空。
3. 评估两处令牌的传递方式，能改则改，不能改就记为残余风险：Codex 和 Gemini 的 API 密钥能否像 Claude 那样不经过环境变量；Claude 和 Codex 的回环 MCP 令牌能否不出现在进程参数里。这取决于各 CLI 是否提供相应的选项，动手前先查证。
4. 更新 `README.md` 的“备份与安全”、`docs/CLAUDE.md`、`docs/GEMINI.md`：说明子进程环境的规则，以及服务环境认证需要的变量如何放行。
5. 同一提交里升级 `buildinfo.Version`。

**验收**

- 适配器测试：在父进程里设置几个假的控制面变量后，断言三种引擎、Git、部署子进程的 `Env` 里都没有它们。
- 重新运行 P5-01 的探测，更新“可达性清单”。
- 如果 P0-07 已经完成，在跨进程验收测试里增加一条用例：让假引擎把自己收到的环境变量名写到文件里，断言其中没有控制面的变量。这条用例走的是内置控制机 Agent 的接入方式，正好覆盖总览“发现的问题”里登记的那一条。P0-07 不是这一步的前置，没有完成时跳过这一项并在“执行记录”里注明。
- 在一台真实服务器上三种引擎各完成一轮对话；如果有服务器使用服务环境认证，也要覆盖到。这一步需要用户配合或授权；做不了时在“执行记录”里注明。

**风险与回滚**

- 提交二可能让依赖某个继承变量的环境失效，例如代理、自定义证书、Node 相关设置、自定义的 CLI 配置目录。白名单以盘点结果为准，并在发布说明里提示配置出口。
- 两个提交各自可回滚，不涉及数据。

**说明**

在内置控制机上，这一步只能防无意泄露，原因见“设计”。文档里不要把它描述成隔离。

### P5-03 隔离技术可行性验证

受决策 D4 约束。这一步的产出是结论，不是产品功能。原型代码不进入产品路径。

**做法**

1. 做一个最小原型：一个包装命令，应用“设计”里的规则草案后执行给定的命令。先做 Landlock，不可行再做 bubblewrap。
2. 在原型里分别运行三种引擎的 CLI，完成下面的检查表，把结果填进“可行性验证结果”。

| 检查项 | 预期 |
| --- | --- |
| 在工作区内读、写、执行 | 成功 |
| 写工作区之外的路径 | 失败 |
| 读 Agent 令牌、各密钥文件、Git 凭据 | 失败 |
| 读其他工作区 | 失败 |
| 连接 Docker socket 和依赖安装助手的 socket | 失败 |
| 在 worktree 里提交 | 成功 |
| 续聊、分叉、编辑重发 | 成功 |
| 通过回环连接 MCP 桥接、提问通道、流式代理 | 成功 |
| 图片输入、技能发现 | 成功 |
| CLI 访问模型接口 | 成功 |

3. 回答下面这些问题。它们目前都只是判断，没有验证过：
   - Landlock 的文件规则和网络规则各自需要多新的内核，目标发行版的默认内核是否满足。
   - Landlock 能否阻止连接一个已经存在的 UNIX socket。如果不能，Docker socket 要靠别的办法挡住，例如让会话进程不带 `docker` 附加组，而这需要特权。
   - Landlock 要求进程不能再获得新特权，这和免密 sudo 冲突到什么程度。
   - bubblewrap 依赖非特权用户命名空间。一些发行版默认限制它，容器里通常也不可用，并且需要额外安装软件包。
   - Codex 的会话进程在启动时还不知道工作区，共享进程要服务多个工作区。规则该在什么时候、按什么范围应用。
   - 各 CLI 自带的沙箱（Codex 的线程级沙箱、Claude 和 Gemini 的沙箱选项）能补上哪一块。它们通常只约束模型运行的命令，不约束 CLI 自己的文件工具。
   - 内置控制机在容器里以 root 运行，上面的方案哪些还成立。
4. 给出结论：推荐方案、它覆盖不了的检查项、对内核和发行版的要求、内置控制机是否支持。把结论写进总览的“决策记录”（D4），并据此修订 P5-04 的步骤细节。
5. 如果没有方案能在目标环境里通过检查表的核心项（凭据不可读、工作区之外不可写），把 P5-04 和 P5-05 改为 `已取消` 或重新设计，并写明原因。

**验收**

- “可行性验证结果”填写完整，结论已和用户确认。
- P5-04 的步骤细节已按结论更新。

**说明**

记录内核和发行版要求时写通用的版本范围，不要写某台机器的具体配置。

### P5-04 可选的会话隔离模式

规模大，分三个提交。前置是 P5-03 的结论和 P2-09（会话进程的启动入口已经收敛到运行器接口）。下面的做法以 P5-03 推荐 Landlock 包装为前提，结论不同时先改这里。

**提交一：沙箱包与包装子命令**

1. 新增只在 Linux 上编译的沙箱包和 Agent 的包装子命令：读取一份规则描述，应用规则，然后执行目标命令。
2. 测试在支持的内核上断言 P5-03 检查表里“失败”的各项确实失败；内核不支持时跳过并打印原因。确认 CI 的运行器是否支持，把结果写进“执行记录”。

**提交二：接入运行器**

1. Agent 配置增加隔离开关，默认关闭。
2. 运行器在启动会话进程时，根据工作区根目录、worktree 的主仓库 Git 目录、引擎的 CLI 配置目录生成规则，通过包装子命令启动。
3. 开关开启但规则无法应用时，会话以明确的错误结束。
4. 心跳上报实际状态：未开启、已开启、不支持及原因。
5. 版本探测、技能发现等短进程一并纳入，或者明确列出不纳入的理由。
6. 同一提交里升级 `buildinfo.Version`。

**提交三：控制面**

1. 保存并通过服务器接口返回隔离状态。
2. 注册和修复服务器时提供开启隔离的选项，与免密 sudo 互斥。
3. 隔离模式下，界面隐藏或禁用确定不可用的入口，并给出原因。

**验收**

- 开关关闭时行为与改动前完全一致：契约测试和三个适配器的测试不需要任何修改。
- 开关开启时，在一台真实服务器上三种引擎各完成：发起、追加、中断、编辑重发、分叉、分叉到 worktree 并提交。同时从会话里运行 P5-01 的探测脚本，凭据类资源全部不可读。这一步需要用户配合或授权；做不了时在“执行记录”里注明，并且不要把步骤标记为 `已完成`。
- 协作测试通过；在隔离模式下完成一次跨工作区的子会话协作。
- P0-07 的跨进程验收测试增加一组开启隔离模式的用例：三种引擎各完成一轮，假引擎尝试读取工作区之外的一个文件并失败。运行环境的内核不支持所选隔离技术时，这组用例跳过并打印原因。

**风险与回滚**

- 最大的风险是某个功能在隔离模式下悄悄失效，例如技能安装、图片临时文件、CLI 的缓存目录。所以默认关闭，先在一台服务器上开启并运行一段时间。
- 回滚不需要回退代码，关闭开关即可。
- 隔离模式改变的是进程能看到什么，不改任何数据和协议。

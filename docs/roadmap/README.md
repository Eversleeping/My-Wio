# Wio 架构调整路线图

更新时间：2026-11-13
基线：提交 `0247c1c`，版本 0.3.12

本目录是一份跨会话、跨 Agent 的执行计划。任何会话（Codex、Claude、Gemini 或人工）都从本文件进入：先读“执行规则”，再在“进度总表”里领取步骤，最后到对应阶段文件里读步骤细节。

## 为什么要调整

Wio 的功能面已经足够宽，当前的主要成本来自结构，而不是缺功能：

1. **三种 AI 引擎是复制出来的。** Codex、Gemini、Claude 在数据库、Store、HTTP、前端各有一套几乎平行的实现，同一个修复经常要做三遍。
2. **几个文件过大。** 后端和前端各有数个两三千行的文件，改动容易冲突，也难以审阅。
3. **控制面与 Agent 之间没有类型契约。** 操作类型是散落的字符串字面量，能力判断靠三十多个按版本号写的门槛函数。
4. **数据库迁移没有版本号。** 每次启动都把全部迁移函数跑一遍，无法判断库处于哪个版本，也无法阻止旧程序连上新库。
5. **没有持续集成。** 八百多个 Go 测试和四百多个前端测试只在本地手动运行。
6. **执行隔离偏弱。** AI CLI 以 Agent 账号的全部权限运行，而协作功能已经能自动创建子会话。

### 推荐顺序

各阶段不是严格串行。按里程碑推进，每个里程碑结束时系统都处于可发布状态。

| 里程碑 | 包含步骤 | 结束时得到什么 |
| --- | --- | --- |
| M1 护栏 | P0 全部、P1 全部、P4-01 | 每次推送自动验证；有一组穿过控制面、Agent 和引擎进程的自动化测试；迁移有版本；操作类型不再是裸字符串 |
| M2 减重 | P3-01 至 P3-07 | 没有超过 1000 行的后端处理器文件；`App.tsx` 只剩应用外壳 |
| M3 内核（控制面） | P2-01 至 P2-05 | 控制面按引擎分支的代码集中到驱动实现里；一套 `/api/sessions` 路由 |
| M4 内核（前端与数据） | P2-06 至 P2-08、P3-08、P3-09 | 一个会话页面外壳；线程表与定时任务表合并 |
| M5 统一入口 | P6 全部 | 一个会话页面列出所有工作区和三种引擎的会话；新建会话时选择引擎 |
| M6 协议与兼容基线 | P4-02 至 P4-05、P2-09、P2-10 | Agent 自报能力；删除历史版本门槛；旧路由与旧表清理完毕 |
| M7 隔离 | P5 全部 | 可选的会话隔离模式 |

依赖关系的要点：

- P0-02 是其余所有步骤的前置。没有 CI 时不做跨文件重构。
- 任何改表的步骤（P2-07、P2-08、P4-02）都依赖 P1 完成。
- P3 的后端拆分（P3-01 至 P3-04）是纯移动，应在 P2 改处理器之前做完，否则两边会反复冲突。
- P2-06（前端外壳）依赖 P3-05 至 P3-07（`App.tsx` 拆分）。
- P4-03（最低 Agent 版本）依赖 P4-02（能力协商）已随某个版本发布并完成全部服务器升级。
- P4-01 放在 M1，在 P3 的后端拆分开始之前做完；P4-04 要等 P3-04 把分支提取成具名方法之后再做。
- P5-01 和 P5-02 不依赖其他阶段，可以随时穿插；P5-04 要等 P2-09。
- P6-01（差异盘点）不依赖任何步骤，应当尽早做，它的结论会影响 P2-05 和 P2-06 的实现；P6 其余步骤要等 P2-06，P6-06 另外要等 P2-07。
- P0-07（跨进程验收测试）要在改动控制面与 Agent 之间链路的步骤之前做完：P2-04、P3-04、P4-02 把它列为前置，P2-09、P4-05、P5-04 通过这三步间接依赖它。

## 产品方向

2026-11-13 用户确定（决策 D9）：**会话入口从“按引擎分页面”转向“按项目和工作区组织”，引擎是创建会话时的一个选择。** 现在导航里 Codex、Gemini、Claude 是三个并列的页面，同一个工作区的会话要到三个页面分别管理。

用户的具体要求：一个页面就能看到所有工作区，不必在三个页面之间来回切换；合并之后，单独任务和协作任务仍然可以自由选择用哪一种引擎。

P0 至 P5 做的是结构调整，新入口本身在 [P6](P6-unified-session-entry.md)。这个决定对前面各阶段的影响有四点：

1. **P2 从“降低维护成本”变成“新入口的前提”。** 跨引擎的混合列表需要统一的读模型（P2-04）和 `/api/sessions` 路由（P2-05），合并后的页面需要会话外壳（P2-06）。在三套各自独立的实现上直接做新入口，等于再叠一层按引擎分支的代码。
2. **M1 至 M4 的顺序不变，之后的优先级有调整。** 原有顺序本来就通向 P2-06。调整的是：M4 里先做 P2-06，再做合表（P2-07、P2-08）和前端数据层（P3-08、P3-09）；新增的 M5（统一入口）排在协议和隔离之前；M6、M7 和 P3-10 不是新入口的前置，排期冲突时让路。需要压缩时间时，P1、P3-03、P3-04 也不是 P2-06 的前置，可以挪到 P2-06 之后、各自的后继步骤之前。
3. **P2 的设计不能把“一个页面只有一种引擎”写死。** P2-05 的列表路由在省略 `engine` 时返回三种引擎的混合列表；P2-06 的外壳用（引擎，会话 ID）标识会话，引擎差异只通过引擎模块表达。P2-06 本身仍然不改用户可见的行为，三个导航入口保留；合并入口是它之后的单独步骤，这样两者可以分别回滚。
4. **新入口的步骤在 P6。** 交互方案的六个事项用户已在 2026-11-13 确认（见 P6 的“已确认事项”），P6-01 只剩差异盘点；P6-02 起依赖 P2-06。两条约束贯穿始终：`/?view=<engine>&thread=<id>` 形式的旧链接继续可用；引擎独有的能力如实呈现，不为了统一而隐藏。

这个方向与 D7 的默认方案一致：新投入集中在会话编排上。是否在会话之上再引入“任务”对象，见待决策事项 D10。

## 执行规则

这些规则对所有会话和 Agent 生效。

### 领取与交接

1. 开始前读本文件的“进度总表”和“待决策事项”，再读目标步骤所在的阶段文件。
2. 只领取状态为 `待开始` 且前置步骤全部 `已完成` 的步骤，或用户明确指派的步骤。
3. 动手前把该步骤状态改为 `进行中`，在“负责”一栏写上日期和会话标识，例如 `11-14 Claude`。
4. 中途停止时，在阶段文件末尾的“执行记录”里写清楚：做完了什么、还剩什么、未提交的改动在哪个分支或 worktree。状态保持 `进行中` 或改为 `受阻` 并写明原因。
5. 状态只有五种：`待开始`、`进行中`、`已完成`、`受阻`、`已取消`。验收项没有全部通过，不得标记 `已完成`。
6. 完成后在总表填上提交号，并在阶段文件的“执行记录”里记下验收命令的实际结果。

### 改动纪律

1. **一步一个提交。** 一个步骤对应一个提交或一组紧密相关的提交，提交信息里带步骤编号，例如 `refactor(httpapi): 按领域拆分 resources.go（P3-02）`。
2. **重构不夹带行为变化。** 标注为“纯移动”的步骤只允许移动代码和调整 import。过程中发现的缺陷记到本文件的“发现的问题”，不要顺手修。
3. **行为先由测试锁定。** 改动某段逻辑前，先确认有测试覆盖当前行为；没有就先补特性测试，单独提交。
4. **保持可回滚。** 涉及数据库的步骤遵循“先扩展、后迁移、最后收缩”：新旧结构并存至少一个发布版本，破坏性清理单独成步。
5. **保持线上兼容。** 控制面要能和落后一个版本的 Agent 工作。HTTP 旧路由在前端切换后至少保留一个发布版本：前端每 30 秒检查一次版本并在不一致时自动刷新，旧页面存在的时间很短，但控制面回滚后会重新提供旧前端，旧路由要在那时仍然可用。
6. **改到 Agent 的代码要同步升级版本号。** 只要改动落在 `cmd/agent` 依赖的包里，就在同一个提交里更新 `internal/buildinfo/version.go` 的 `Version`。
7. **提交和推送需要用户授权。** 未获明确授权时只在工作区完成改动并报告。
8. **计划与现实不符时先改计划。** 本目录引用的文件和符号以基线提交为准。发现文件已移动、步骤已过时或拆分不合理，先更新阶段文件再继续。

### 并行

- 多个 Agent 同时工作时各用独立 worktree，并且只领取互不重叠的步骤。下表列出会互相冲突的组合。
- 更新进度总表时只改自己那一行，并尽快提交，减少合并冲突。

| 不要并行的组合 | 原因 |
| --- | --- |
| P3-01、P3-02 与任何改 `internal/httpapi` 处理器的步骤 | 同一批文件的大范围移动 |
| P3-03 与 P1 的任何步骤 | 都在改 `internal/store/store.go` |
| P3-05 至 P3-07 与 P2-06 | 都在改 `web/src/App.tsx` 和三个会话页面 |
| P6-02 至 P6-04 与 P2-06、P3-08 | 都在改会话页面的外壳、导航和取数方式 |
| P2-07 与 P2-08 | 都在改线程相关表和外键 |
| P3-08 与 P2-06 | 都在改页面的取数方式；P3-08 不要碰三个会话页面 |
| P3-10 与任何新增界面文案或样式的步骤 | `i18n.tsx` 和 `styles.css` 几乎每个功能提交都会改 |
| P4-01 与 P3-01 至 P3-04、P2-03 至 P2-05 | P4-01 会改到几乎所有引用操作类型的后端文件，并使纯移动校验和失效 |

### 通用验收

除非步骤另有说明，每个步骤完成前都要通过下面全部命令。

```bash
npm --prefix web run build      # 生成 web/dist，Go 构建会嵌入它
go vet ./...
go test ./...
npm --prefix web test
npm --prefix web run typecheck
```

涉及 `internal/store` 的步骤另外运行 `make test-postgres`。涉及页面交互的步骤另外运行 `npm --prefix web run e2e`。

各台机器的工具链路径、镜像源等本地差异不写进本目录，由各会话自己的本地备忘负责。

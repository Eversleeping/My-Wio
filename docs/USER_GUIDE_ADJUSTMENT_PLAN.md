# Wio 用户体验调整计划

> 来源：`docs/USER_GUIDE.md` 的用户流程走查
>
> 更新时间：2026-08-04
>
> 当前状态：按必要性评估修订，3 项待开始、3 项暂缓、1 项已完成；未新增 P0

本计划承接用户使用手册走查中发现的产品体验问题。它只记录后续产品调整，不把本地启动环境中的缺少配置、示例数据或截图状态当作产品故障。

## 1. 计划目标

围绕管理员最容易产生判断成本的三类问题进行改进：

1. 用户能够找到排队中、执行中和已结束的异步操作。
2. 用户在部署配置发生变化时，能够看到可信的差异，并确保历史记录和回滚基线不被当前配置覆盖。
3. 用户能够通过按钮前置条件和资源筛选快速判断下一步动作。

## 2. 范围和约束

- 本计划聚焦用户可见的流程、状态、提示、筛选和部署配置可信度；实时事件、长列表性能、通用确认框和可访问性基础设施已经在 [UX 优化实施计划](UX_OPTIMIZATION_PLAN.md) 中记录，不重复拆分。
- 所有新提示必须兼容空数据、服务器离线、权限不足、Agent 未安装和功能依赖缺失等状态。
- 故障摘要、部署快照、差异视图和界面截图不得展示 API Key、Git Token、私钥、SSH 密码或 Vault 明文值。
- 任何“快捷处理”只能跳转到已有操作入口或打开已有确认流程，不新增任意 Shell 执行能力。
- 产品实现完成后，必须使用真实功能状态重新采集截图；本地模拟截图只能用于布局和交互验收，不能证明生产能力可用。
- 没有真实用户反馈、工单或资源规模证据的 P2 项目不得提前扩展为大型模块；先保留最小可行入口。

## 3. 优先级和状态

优先级含义：

- **P0**：影响数据可信度、安全边界或核心操作正确性，当前没有新增 P0 项目。
- **P1**：显著减少日常操作成本，或修复会影响部署历史和回滚判断的基础能力。
- **P2**：提升资源较多时的查找效率或监控联动体验；需要先有真实使用证据。

状态统一使用：`待开始`、`进行中`、`已完成`、`受阻`、`暂缓`。已存在的基础能力不再重复列为待办；未通过对应验收项时不得标记为“已完成”。

## 5. 详细调整项

### UX-01 首次使用空状态与下一步提示

**必要性判断**：完整向导对单管理员产品的首次使用场景投入偏大。当前先暂缓，只有在真实用户反复卡在配置顺序或支持记录明显增加时再恢复。

**后续方向**：

- 总览页的空状态可以给出一条最直接的下一步入口，例如先创建 Codex 凭据或注册第一台服务器。
- 每个空状态最多展示一个主动作和一个前置条件说明，不新增跨页面的流程状态机。
- 需要时再补充轻量的完成标记，不提前建设完整配置进度模型。

**恢复条件**：有真实用户反馈、工单或使用数据证明用户经常因配置顺序无法继续。

**暂缓期间的验收**：现有空数据页面不能出现无目标的空白区域；主入口和必要前置条件应能被用户直接理解。

### UX-02 最近异步操作中心

**问题**：服务器、项目、Git、Codex 和部署分别展示操作状态，用户需要在多个页面寻找 `queued`、`running` 或失败记录。

**调整内容**：

- 增加“最近操作”入口，第一版只做跨资源的只读聚合，展示操作类型、资源、服务器、当前状态、开始时间、最近消息和更新时间。
- 支持按状态查看 queued、delivered、running 和终态操作；默认优先展示未完成操作。
- 每条记录提供回到资源详情或查看日志的入口；取消和重试只有在对应操作已有明确接口和语义时才展示，不新增通用取消/重试协议。
- 连接恢复或历史补同步后，列表不得重复展示同一操作。
- 对长时间未变化的操作显示“等待 Agent”“等待远程仓库”或其他可确认的阶段信息；没有可靠阶段时显示通用等待状态，不猜测原因。

**依赖**：现有操作状态、事件流、项目/工作区操作详情和部署日志；需要增加一个只读聚合接口，并统一资源链接和操作类型命名。

**验收标准**：

1. 从任一页面都能打开最近操作，并能看到当前管理员有权限查看的未完成操作。
2. 同一操作在事件推送、刷新和重连后只出现一条。
3. 点击记录可以回到正确资源；无权限或资源已删除时显示可理解的结果。
4. 操作完成后保留足够的最近历史，但不会无限加载全部历史。

### UX-03 显示按钮禁用原因

**问题**：服务器离线、缺少凭据或存在并发操作时，部分按钮会被禁用，但用户不一定知道前置条件。

**调整内容**：

- 把禁用原因作为各页面的交互验收规则，优先覆盖服务器更新、凭据修改、部署、工作区移动/复制和 Codex 会话等高频入口。
- 在禁用按钮旁或其可访问名称中显示简短原因，例如“需要服务器在线”“需要先创建 Codex 预设”“当前工作区有写操作正在执行”。
- 对多个原因按优先级只显示最直接的阻塞原因，并提供查看完整条件的提示。
- 条件恢复后实时更新按钮状态和提示，不要求用户手动刷新。
- 区分“暂时不可用”“当前版本不支持”和“当前管理员没有权限”。

**依赖**：前端需要拿到稳定的能力、在线状态、权限和操作锁定信息；后端错误码和前端文案需要建立映射。该项不单独引入新的全局状态系统。

**验收标准**：

1. 每个已纳入范围的禁用操作都能解释至少一个可行动原因。
2. 提示不泄露凭据值、内部路径或不应暴露的服务器信息。
3. 键盘和屏幕阅读器能够读取按钮名称与禁用原因。
4. 空数据、离线和能力缺失场景的提示互不混淆。

### UX-04 最小故障摘要

**必要性判断**：当前已有通用剪贴板能力和错误展示，但还没有证据表明需要跨页面的完整诊断协议。先暂缓完整方案，避免在错误模型和脱敏规则尚未统一时生成看似完整但不可靠的摘要。

**后续方向**：

- 近期只在已有操作详情中提供复制操作 ID、状态和错误消息的入口。
- 只有在确定统一错误模型、操作上下文和脱敏规则后，才扩展为跨页面诊断摘要。
- 摘要需要覆盖 API Key、Git Token、SSH 私钥、密码、Vault 值、Authorization 头和疑似密钥字段，并通过专门的脱敏测试。

**恢复条件**：出现重复工单、人工拼接上下文耗时明显，或真实用户明确需要将失败信息交给维护人员。

**暂缓期间的验收**：现有复制入口应提供成功、失败和浏览器不支持剪贴板时的反馈；不得把未脱敏的原始错误对象直接放入剪贴板。

### UX-05 部署配置快照与变更审查

**问题**：部署目标可以被更新，而部署历史和回滚需要依赖过去的配置。只有比较界面而没有不可变快照，用户看到的差异可能无法证明历史部署实际使用了什么。

**调整内容**：

- 每次成功部署保存不可变的配置快照，至少包括来源类型、服务器/工作区、仓库和 Git 引用、解析后的 commit、Compose 文件、构建模式、外部访问配置、健康检查配置以及 Vault 密钥集的标识和版本。
- 部署历史优先读取自身快照，不再通过当前部署目标的可变字段解释过去的环境、访问地址或其他配置。
- 编辑部署目标或发起部署前，展示当前配置与上一次成功快照的差异；没有成功基线时明确显示“无可对比版本”。
- Vault 只展示名称和版本/更新时间，不保存或展示环境变量明文。
- 回滚必须绑定到对应的历史发布和配置快照；历史快照缺失或不兼容时明确失败，不能静默使用当前目标配置。

**依赖**：部署配置快照表或版本字段、成功部署记录、迁移策略和回滚命令载荷；需要明确旧历史记录无法恢复快照时的展示方式。

**验收标准**：

1. 修改部署目标后，历史部署仍显示其创建时的环境、访问地址和配置摘要。
2. 只修改 Git 引用时，差异视图只突出相关字段和解析出的 commit 变化。
3. 修改多个字段时，用户能逐项看到变化来源；替换 Vault 时不出现任何密钥明文。
4. 首次部署、失败部署和回滚后再次部署均有明确的基线说明。
5. 回滚使用与目标历史发布匹配的 Compose 配置和发布目录；缺少快照时给出可操作的失败原因。

### UX-06 基础项目和工作区筛选

**问题**：项目数量增加后，仅依靠分页和手工浏览难以找到特定服务器、环境或状态的工作区；Codex 会话也难以按活动状态定位。

**调整内容**：

- 项目列表第一期支持按项目名称、服务器和项目状态筛选。
- 工作区列表第一期支持按路径、服务器和 Git 状态筛选。
- Codex 会话侧边栏先保留已有活动/归档切换；“最近活动”“有未提交改动”“有待审批”列为后续扩展，不与项目筛选同时交付。
- 筛选条件在刷新和分页时保持一致；空结果显示当前筛选条件和清除入口。
- 移动端将筛选项收纳到可关闭的筛选面板，避免挤压列表内容。

**依赖**：项目和工作区列表接口的过滤、分页和排序契约；第一期不得为了筛选触发逐条 Agent 请求。

**验收标准**：

1. 项目名称、服务器和状态筛选结果与列表中的资源状态一致，不把分页外资源误计入当前页。
2. 清除筛选后能恢复默认列表；浏览器刷新不会丢失必要的筛选上下文。
3. 无权限资源不因筛选条件而泄露名称或数量。
4. 大量项目和会话下，筛选不会触发逐条 Agent 请求。

### UX-07 危险操作影响范围

**现状**：该项不再作为新的产品调整。统一确认框、项目删除预检、工作区删除预检和阻塞项展示已经完成，具体实施记录见 [UX 优化实施计划](UX_OPTIMIZATION_PLAN.md)。

**维护审计**：

- 新增危险操作必须继续提供影响说明，并通过统一确认框触发。
- 每次涉及删除、回滚或容器清理的功能变更，都要核对远程仓库、观察工作区、命名卷和部署历史的保留规则。
- 发现实际执行范围与预检或确认文案不一致时，再创建独立修复项，不重新打开本条目。

**完成依据**：现有删除预检包含工作区、受管/观察模式、脏状态、活动操作、Codex 任务、部署和远程仓库保留信息；通用危险确认要求调用方提供影响说明。

### UX-08 监控直达入口

**必要性判断**：指标与操作的因果关联目前缺少可靠数据模型。先暂缓“行动建议”和自动推断，只保留未来可以低成本实现的直达入口方向。

**后续方向**：

- 监控页可以提供查看当前服务器详情、项目列表或部署列表的直接入口。
- 入口只携带服务器和时间范围等确定上下文，不把最近操作直接宣称为异常原因。
- 不自动重启容器、清理文件或修改服务器配置。

**恢复条件**：明确指标、告警、操作和部署之间的关联字段、时间窗口和误报处理方式，并有真实用户反馈证明联动有价值。

**暂缓期间的验收**：监控无数据或告警已解决时，页面仍保持正确空状态；不得出现没有可靠目标的“建议操作”按钮。

## 6. 实施阶段

### 阶段 0：证据和数据模型确认

先确认真实使用规模、失败反馈和部署历史需求；同时为 `UX-05` 设计部署配置快照和旧数据迁移策略。没有数据证据的 `UX-01`、`UX-04` 和 `UX-08` 保持暂缓。

**阶段验收**：计划中明确哪些工作是新增能力、哪些已有能力只需维护，并确认快照字段不包含任何 Vault 明文。

### 阶段 1：部署可信度

实施 `UX-05`。先保证部署历史、差异和回滚使用可信的不可变基线，再建设差异界面。

**阶段验收**：覆盖首次部署、成功部署后修改目标、失败部署、回滚、旧历史无快照和 Vault 替换等场景。

### 阶段 2：操作可发现性和资源查找

实施 `UX-02`、`UX-03`、`UX-06`。先让用户找到正在发生的操作、理解按钮为什么不可用，再处理项目和工作区规模增长后的查找问题。

**阶段验收**：使用在线、离线、能力缺失、并发写操作、空筛选结果和重连补同步等数据完成桌面端与移动端验收。

### 阶段 3：按证据恢复暂缓项

只有达到恢复条件后，才评估 `UX-01`、`UX-04` 和 `UX-08`；每项单独立项，不能因为阶段开始就默认全部实施。

**阶段验收**：每个恢复项都要有对应的真实反馈、最小交付范围和失败/空状态验收，不以本地模拟截图作为必要性证据。

## 7. 测试和交付要求

- 前端组件测试覆盖默认、空数据、加载、失败、禁用和权限不足状态。
- 涉及接口的调整增加请求参数、响应字段、权限和分页契约测试。
- 部署快照增加历史一致性、目标更新、回滚匹配、旧记录缺失快照和敏感字段不落盘的测试。
- Playwright 使用本地 API/WebSocket mock 覆盖桌面端和移动端核心流程；未匹配请求必须显式失败。
- 所有涉及敏感数据的功能增加脱敏回归测试，测试数据使用假密钥、假 Token 和假路径。
- 实现后重新采集对应用户手册截图；截图只证明界面状态，不替代接口、权限和生产部署验收。
- P2 项目在实施前必须补充真实反馈、工单或资源规模证据；没有证据时保持“暂缓”。
- 完成每个条目的功能测试、边界测试和视觉复核后，才将状态从“进行中”改为“已完成”。

## 8. 维护方式

每次开始实现、完成实现、完成测试或发现范围变化时更新本计划。代码变更遵循仓库 `AGENTS.md` 中的提交规范；提交前检查 diff，未经确认不自动提交。
